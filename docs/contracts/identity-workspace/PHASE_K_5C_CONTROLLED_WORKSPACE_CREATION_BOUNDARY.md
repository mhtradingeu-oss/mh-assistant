# Phase K-5C — Controlled MH Trading Workspace Creation Boundary

## Decision

Phase K-5C introduces one backend orchestration boundary for creating only the `MH Trading`
Workspace. The boundary cannot create or mutate a Project, Project identity, relationship,
binding, registry, or migration artifact.

## Authority map

| Concern | Authority |
| --- | --- |
| Workspace record schema | Workspace Contract |
| Workspace ID generation, creation, and persistence | Workspace Runtime |
| Workspace creation approval evidence | Governance Approval Engine |
| Dry-run, exact-plan check, delegation, and replay outcome | Controlled Workspace Creation Boundary |
| Result and plan schema; immutable return values | Controlled Workspace Creation Contract |
| Frontend | Projection only; no role in creation |

The boundary contains no filesystem writer. Its only mutation delegation is
`WorkspaceRuntime.createWorkspace`.

## Controlled request

The request has exactly two fields: `workspace_name` and `ownership_evidence`.
`workspace_name` must be `MH Trading`. Ownership evidence must come from the governed K-5F.1
handoff and describe an exact Governance-Approval-Engine-owned, approved `CREATE_WORKSPACE`
decision scoped to the same Workspace and identified by the durable approval ID. A copied or
caller-crafted request is rejected.

The evidence is not copied as an authorization payload. Workspace Runtime persists only the
bounded `workspace_creation` evidence reference defined by the existing Workspace Contract.

## Execution

1. Validate the exact request and Governance Approval Engine provenance.
2. Ask Workspace Runtime whether that creation evidence already owns a Workspace.
3. Return an immutable deterministic dry-run plan without writing.
4. On apply, regenerate the dry run and require byte-equivalent approved plan content.
5. If evidence already resolves, return `ALREADY_EXISTS`.
6. Otherwise delegate creation to Workspace Runtime with `UNCLAIMED` operational ownership,
   no relationships, and the single Governance Approval Engine creation reference.

The Workspace ID is generated by Workspace Runtime and is intentionally absent from the dry-run
plan.

## Safety boundary

- No Project creation or mutation.
- No HairoticMen mutation.
- No Project identity or `project_id` generation.
- No relationship or binding creation.
- No registry write.
- No migration.
- No frontend writer.
- Replay by the same creation evidence does not create a duplicate Workspace.

The concurrency guarantee remains aligned with the existing Workspace Runtime single-writer
model: process-local serialization, without a cross-process transaction guarantee.

## Verification

Run:

```sh
node scripts/verify-controlled-workspace-creation.js
```

The K-5F.1-compatible suite proves a deterministic no-write dry run, governed handoff provenance,
raw caller-request rejection, immutable results, and unchanged Project/HairoticMen data. It does
not invoke apply or create a Workspace.
